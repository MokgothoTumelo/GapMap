# GapMap core — the artefact format

The shared, runtime-agnostic core of GapMap: the artefact format (the contract
between the Learning Companion and the rest of the product) and its JSON
Schemas. Pure data and docs — no JavaScript logic, no environment
dependencies — so it imports cleanly into both the browser client and the
Companion.

## Layout

```
core/
  schema/                           # JSON Schemas — the LLM-boundary contract
    assessment.schema.json          #   Diagnostic/Practice union
    assessment-common.schema.json   #   shared Assessment metadata
    assessment-item.schema.json     #   shared Item contract
    diagnostic.schema.json          #   Diagnostic constraints
    practice.schema.json            #   Practice constraints
    attempt.schema.json             #   learner Responses and scores
    concept-graph.schema.json       #   the Subject's prerequisite map (ADR-0006)
  scoring.js                        # per-Concept rollup → Gap Map (Mastery)
  learning-path.js                  # Gap Map + Concept Graph → root-first Learning Path (ADR-0006)
  validate.js                       # cross-field semantic checks the schemas can't express
  README.md                         # this file
```

## The Concept Graph (ADR-0006)

The Subject's **Concept Graph** — one frozen artefact per Subject — records the
**Prerequisite** edges between its Concepts, spanning grades where a Concept
builds on earlier years' work (each node may carry its origin `grade`). It is
Subject-level curriculum knowledge, not per-Learner state: consumers that know
the Subject (the pages, the Companion's tool executor) load it and inject it
into the derivation.

The **Learning Path** is a pure derivation in `learning-path.js`:
`(gapMap, graph, mistakeKinds) → { path, rootCauses }` — topologically ordered
roots-first, severity as tie-break, each entry carrying `origin`, `blocks`,
`blockedBy`, and (when the artefacts carry Mistake-Diagnosis kinds) `evidence`.
It is computed on read, exactly like the Gap Map rollup, and never stored as a
per-Learner artefact. Without a graph the order is severity alone; without
kinds the evidence is simply absent — the UI says what the data supports and
nothing more. Path *wording* lives in the render layer; this module returns
data, not sentences.

A **Foundational Gap** is a Knowledge Gap on a below-grade Prerequisite — the
Mathematical Literacy → Algebra story, and the reason the graph spans grades.

## Assessment and attempt

- The **assessment** is generated by the LLM and frozen for that attempt.
  Regenerating it must not clobber in-progress answers or attempt history.
- The **attempt** is written by the app as the learner answers. It carries
  responses, per-concept scores, and generated "why did I get this wrong"
  feedback.
- The artefact the UI shows is `assessment ⨝ attempt` joined by `item_id`.
- Each Item can provide a `correct_explanation` and answer-specific
  `wrong_explanations` for immediate feedback and agent-generated guidance.
  Each wrong explanation may carry a Mistake-Diagnosis `kind` (`misread`,
  `procedure`, `concept`, or `prerequisite`; a `prerequisite` kind names the
  blocking Concept) — the kinds roll up into the Gap Map's root-cause readout
  via `learning-path.js`'s `mistakeKindsByConcept`.

## The Concept tag is the bridge

Every item carries a `concept`. Scores roll up by concept, and the rollup
*is* the Gap Map. Without `concept`, a quiz is just a quiz; with it, a quiz
becomes a measurement of the learner's Knowledge Gaps. `concept` is required on
every item and must match a name in the assessment's top-level `concepts[]`.

## Format boundary

On disk: YAML (human-inspectable). At the LLM boundary: the assessment JSON
Schema, so generation is validated. Convert at the boundary — don't hand-parse
free-form YAML from the model.

## Status thresholds (app policy)

- `strong`  ≥ 80%
- `improve` 50–79%
- `weak`    < 50%

## Integration points (solved)

These are decided. They are documented here so the contract between the agent
service and the rest of the product is prominent, not buried in code.

### What gets passed to the model (Companion → LLM)

- **Companion chat** (wired locally; live model injected): the system prompt —
  a patient learning companion for Grade 12 Mathematics, in the Learner's
  Language, explaining simply, using the Learner's name naturally when it's in
  the context, connecting explanations to the Learner's Knowledge Gap and
  Learning Path, not inventing Diagnostic results, and — via the
  `getPlatformHelp` tool — grounding platform guidance in the Learner's state
  (their grade + Subject, whether a Gap Map exists, whether an unattempted
  Practice is waiting) — plus the conversation transcript. The Learner store
  supplies the current Learner context — the mock store offline, the
  Firestore-backed adapter in a live session; the Firebase AI Logic
  model is an optional runtime seam.
- **Assessment generation** (implemented locally; live model adapter ready):
  Subject, Concepts, assessment type (Diagnostic / Practice), target
  Concept (for Practice), Language, Explanation Level, and item-count
  constraints. Items' `wrong_explanations` may carry Mistake-Diagnosis kinds.
- **Concept Graph generation** (local + model adapters in
  `frontend/js/concept-graph-generator.js`): the Subject, and — when a
  Learner's graph is missing — the model proposes nodes and prerequisite
  edges, which are schema- and semantics-validated and frozen per Subject.
  The demo Subject's graph is authored YAML (`data/subjects/`), served by the subject store (`frontend/js/subject-store.js`).
- **Mistake Diagnosis** (planned): the Item, the Learner's Response, the
  correct answer, and the `wrong_explanations` seed.

### What the model produces (LLM → agent service)

Validated against `core/schema/` at the boundary:

- **Companion chat**: a reply (text), streamed to the panel.
- **Assessment generation**: an Assessment artefact — Diagnostic or Practice —
  carrying Items with correct answers, Concept tags, and
  Mistake-Diagnosis seeds (`wrong_explanations`, optionally with a `kind`).
  Local and model-backed generation validate the semantic contract; the live
  boundary must also enforce `assessment.schema.json` (the `oneOf` union of
  the two kinds).
- **Concept Graph generation**: the Subject's nodes and prerequisite edges —
  validated against `concept-graph.schema.json` and `validateConceptGraph`
  (endpoints exist, no cycles, no self-edges) before anything renders from
  it. The model proposes the edges; the Learner inspects the artefact.
- **Mistake Diagnosis**: planned explanation of *why* a wrong Response is wrong
  (the type of mistake), per the `wrong_explanations` shape — now with its
  kind.

The **attempt is not model-produced** — it is app-written: the learner's
Responses, the per-Concept Mastery rollup (the Gap Map), and generated Mistake
Diagnoses.

### How that gets answered (output → learner → next step)

- **Companion reply**: streamed to the panel.
- **Assessment**: the generated artefact is frozen; the learner attempts it;
  the app writes the attempt; the per-Concept rollup produces the **Gap Map**;
  the Gap Map and the Subject's **Concept Graph** drive the **Learning Path**
  (roots first, evidence-backed); **Practice** targets one Concept on
  the path; the Learner re-measures by **retaking the Diagnostic**, and the
  fresh Gap Map shows whether Mastery moved. A separate Retest Assessment kind
  was part of this format and has been removed: re-measuring by retaking the
  Diagnostic is the flow, and the extra kind reinforced a misunderstanding of
  it. The Practice screen still runs on `concept.html`'s in-page Concept bank
  rather than on a Practice artefact.
- The **Concept tag is load-bearing**: it is what makes the rollup a Gap Map.
  The assessment is frozen; the attempt is append-only.

## Quantum Adaptive Practice and the Quantum Study Plan

Two features run real quantum algorithms on a **state-vector simulator**
(`core/quantum-sim.js`). Everything is simulated on a classical computer in the
browser — no quantum hardware or remote quantum service is used, and the UI
says so. Full plain-language walkthrough: [`docs/QUANTUM-EXPLAINED.md`](../docs/QUANTUM-EXPLAINED.md).

**Quantum Adaptive Practice** (`core/quantum-adaptive.js`) — which Concept next?

- The Diagnostic's scores and Mistake Diagnoses give a classical starting
  probability per Knowledge Gap.
- **Amplitude encoding** loads those probabilities into ⌈log₂N⌉ qubits.
- An **oracle** marks root-cause Concepts (they block other weak Concepts in
  the Concept Graph, or a Mistake Diagnosis names them as the missing
  prerequisite). One **phase-tuned amplitude-amplification** round makes them
  interfere constructively, stopping at ~75% of the probability instead of
  overshooting. It is kept only if the root-cause probability really rose.
- The register is **measured** (Born rule, seeded → reproducible). The most
  frequent outcome is the Concept the state collapses onto. Practice Items are
  then ranked by Mistake-Diagnosis kind and staged repair → transfer → check.
- The plan records the circuit it ran (`plan.quantum.circuit`).

**Quantum Study Plan** (`core/quantum-qaoa.js`) — which K Concepts this week?

- One qubit per weak Concept (max 10). The choice is written as a **QUBO**
  (reward for big gaps and Concepts that unlock weak dependents; penalties for
  the wrong number of Concepts and for skipping a prerequisite), converted to an
  **Ising** cost, and solved with a 2-layer **QAOA** circuit.
- A classical optimiser tunes the angles (CVaR objective); the circuit is then
  measured and the cheapest *valid* plan wins. The result is checked against
  exhaustive classical search, and the dashboard shows that check.
- The chosen Concepts are ordered roots-first with `buildLearningPath()`.

Honesty rules: no speed-up is claimed (with ≤10 Concepts brute force is
instant); the starting scores are an ordinary heuristic; the value is a correct,
hardware-portable formulation plus a verified result.

## Resolved follow-ups

- **Domain logic relocation.** The scoring / per-Concept rollup / Mastery
  classification and the cross-field semantic validators live in `core/` as ES
  modules (`scoring.js`, `validate.js`), imported by both the browser client
  (via `frontend/js/assessment-renderer.js`) and, when wired, the Companion.
  The browser was migrated from classic `<script>` globals to ES modules; the
  demo is verified by a Playwright baseline (`tests/demo.spec.js`).
- **Schema / validator unification.** The JSON Schemas are the structural
  contract, enforced by ajv (`tests/validate.spec.js`, and at the LLM boundary
  when generation is wired). `core/validate.js` is the
  thin, shared, runtime-agnostic layer for the cross-field semantic checks the
  schemas cannot express (the Concept-tag bridge, wrong-explanation sanity)
  — one source of truth for structure (the schemas)
  and one for semantics (`validate.js`), not two hand-mirrored copies that
  drift. Trade-off: the browser validates semantics only on load; structure is
  ajv's job, enforced in tests now and at the server boundary later (the
  browser loads trusted demo data or server-validated artefacts). Making the
  schemas a usable contract also fixed their `$id`s (to match the `$ref`s) and
  the `correct` / `wrong_explanations.answer` `oneOf` (an integer is a number,
  so `oneOf` matched two — now a type array).
- **CDN localization.** `js-yaml` is vendored at `frontend/vendor/js-yaml.min.js`
  (4.3.1); the pages load the local copy, so the demo and the Playwright
  baseline are fully offline.
