The repo is currently at the prototype stage but that is not a license to treat the code as disposable, write clean, maintainable code and survey the structure and relevant README.md + CONTEXT.md docs before producing any code. 

Survey means actually reading the docs that touch the work: the root README.md is the hackathon submission and carries the product vision, user journey, and MVP scope; CONTEXT.md is the domain glossary and the authority on what things are called; docs/ and docs/adr/ hold the plan and the architectural decisions; core/README.md explains the format the whole product is built on. When a decision already exists in those pages, follow it; when you make a new one, record it there so the next agent doesn't have to rediscover it.

Architectural decisions (docs/adr/) are binding on future sessions — once recorded they become constraints, not suggestions. Never record an ADR without explicit user approval of its full text, including the rationale and consequences. When proposing a decision, surface the implications of every potential inclusion before it is approved: a model pin, a default, a "must never" rule, or a deadline written into an ADR constrains every later session, so the user must see and agree to those implications before the ADR is recorded. If an ADR already contains inclusions the user never approved, correct it rather than propagating them.

Language is part of the design. The glossary resolves the ambiguities, so use its canonical terms — Learner, Subject, Concept, Assessment, Diagnostic, Practice, Retest, Item, Response, Score, Mastery, Knowledge Gap, Gap Map, Learning Path, Mistake Diagnosis, Language, Explanation Level, Learning Companion — and avoid the banned ones: student, user, quiz, test, topic, feedback, weakness, level on its own. A Score is a percentage; a Knowledge Gap is a Concept the Learner hasn't mastered; Practice drills one Concept and Retest re-measures it; the Learning Companion is not a chatbot. If a concept needs a new word, update the glossary and the code together, not one without the other.

The artefact format is the core of the product and it is two files, not one: an assessment (LLM-generated, frozen for the attempt) and an attempt (app-written Responses, per-Concept rollup, Mistake Diagnoses) joined by item_id. The Concept tag is load-bearing — every Item covers exactly one Concept and the rollup is the Gap Map; an Item without a Concept is a schema violation, not a convenience. Assessments are never mutated and attempt history is append-only; demo YAML in core/demo-data/ is inspectable sample data, not application state; the JSON Schemas in core/schema/ are the contract at the LLM boundary and must move with the format.

The server is deliberately minimal: serve.mjs is a static-only file server — no router, no API routes, no response seam. The seam-based Node adapter (server/) and its agent mounting were retired with the Firebase AI Logic decision (docs/adr/0004-firebase-ai-logic.md); static hosting may later move to Firebase Hosting, and that should stay a swap, not a rewrite.

The Learning Companion (frontend/agentPanel/) uses Firebase AI Logic (docs/adr/0004-firebase-ai-logic.md) — browser-owned orchestration via the Web SDK with a managed proxy holding the key; the Node agent service and stored credential (docs/adr/0002-google-gemini-stored-credential.md) are retired. The panel uses a request-scoped browser client and a live model pool; it must surface missing configuration and provider failures rather than masking them with a fabricated response. The static demo and tests can run key-free via `?agent=off`; live smoke coverage is a separate script — see docs/companion.md. Never make the test suite require a live project or key. The React/PostgreSQL/Python stack in the README is planned, not present: don't pretend it exists, but don't write anything that makes it harder to land — moving to Postgres is supposed to be a serialization change, not a model change.

Run the app with ./serve.sh (or npm start from the repo root); serve.mjs serves the repo root statically, so the demo screens at the root (index, login, signup, setup, learn, dashboard, diagnostic) and the frontend/ modules are just files. The demo path is the point of the project — Diagnostic → Gap Map → Learning Path → Practice → Retest — keep it working, keep it inspectable, and keep the demo data readable by hand: if a change makes the artefacts harder to show a judge, it is a regression even when tests pass.
