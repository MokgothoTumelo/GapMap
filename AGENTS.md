The repo is currently at the prototype stage but that is not a license to treat the code as disposable, write clean, maintainable code and survey the structure and relevant README.md + CONTEXT.md docs before producing any code. 

Survey means actually reading the docs that touch the work: the root README.md is the hackathon submission and carries the product vision, user journey, and MVP scope; CONTEXT.md is the domain glossary and the authority on what things are called; docs/ and docs/adr/ hold the plan and the architectural decisions; core/README.md explains the format the whole product is built on. When a decision already exists in those pages, follow it; when you make a new one, record it there so the next agent doesn't have to rediscover it.

Architectural decisions (docs/adr/) are binding on future sessions — once recorded they become constraints, not suggestions. Never record an ADR without explicit user approval of its full text, including the rationale and consequences. When proposing a decision, surface the implications of every potential inclusion before it is approved: a model pin, a default, a "must never" rule, or a deadline written into an ADR constrains every later session, so the user must see and agree to those implications before the ADR is recorded. If an ADR already contains inclusions the user never approved, correct it rather than propagating them.

Language is part of the design. The glossary resolves the ambiguities, so use its canonical terms — Learner, Learner Profile, Subject, Concept, Assessment, Diagnostic, Practice, Item, Response, Score, Mastery, Knowledge Gap, Gap Map, Learning Path, Mistake Diagnosis, Language, Explanation Level, Learning Companion — and avoid the banned ones: student, user, quiz, test, topic, feedback, weakness, level on its own. A Score is a percentage; a Knowledge Gap is a Concept the Learner hasn't mastered; Practice drills one Concept, and re-measurement is retaking the Diagnostic; the Learning Companion is not a chatbot. If a concept needs a new word, update the glossary and the code together, not one without the other.

The artefact format is the core of the product and it is two files, not one: an assessment (LLM-generated, frozen for the attempt) and an attempt (app-written Responses, per-Concept rollup, Mistake Diagnoses) joined by item_id. The Concept tag is load-bearing — every Item covers exactly one Concept and the rollup is the Gap Map; an Item without a Concept is a schema violation, not a convenience. Assessments are never mutated and attempt history is append-only; demo YAML in core/demo-data/ is inspectable sample data, not application state; the JSON Schemas in core/schema/ are the contract at the LLM boundary and must move with the format.

The server is deliberately minimal: serve.mjs serves the repo root statically and exposes exactly one API route, GET /api/download?id=<id> — a server-side whitelist that streams an official past paper for the Library (unknown ids 404, upstream failure 502, and the frontend supplies only an id, never a URL). That route is the only server behaviour: no router, no sessions, no response seam, and a second route needs a decision. The seam-based Node adapter (server/) and its agent mounting were retired with the Firebase AI Logic decision (docs/adr/0004-firebase-ai-logic.md — amended 2026-09-16 to record the one route); static hosting may later move to Firebase Hosting, and that should stay a swap, not a rewrite — the download route would need the host's equivalent there.

Firebase Authentication is the production account source of truth: signup.html and login.html create/sign in accounts with email/password, then require an EmailJS OTP before the GapMap app-session snapshot is written to `gapmap_user`. Firebase Authentication owns passwords; Cloud Firestore owns `learners/{uid}` profiles and the Learner's Assessments, Attempts, Diagnostic summaries, Practice history, and Companion transcript. frontend/js/auth-guard.js (`GapMapAuth`) remains the page-guard and local-session helper. The active Subject and active Language are Learner Profile preferences, switchable in the nav (`GapMapAuth.mountSubjectSwitcher` / `mountLanguageSwitcher`); the whole Profile — identity and preferences — is inspectable and modifiable on profile.html, reached through the avatar menu (`GapMapAuth.mountProfileMenu`) which also holds Log out. Browser tests and scripts must seed the lightweight session for protected pages (see tests/helpers/session.js) rather than create real Firebase accounts. The legacy `gapmap_users` account registry is no longer used.

The Learning Companion (frontend/agentPanel/) uses Firebase AI Logic (docs/adr/0004-firebase-ai-logic.md) — browser-owned orchestration via the Web SDK with a managed proxy holding the key; the Node agent service and stored credential (docs/adr/0002-google-gemini-stored-credential.md) are retired. The panel uses a request-scoped browser client and a live model pool; it must surface missing configuration and provider failures rather than masking them with a fabricated response. The static demo and tests can run key-free via `?agent=off`; live smoke coverage is a separate script — see docs/companion.md. Never make the test suite require a live project or key. The React/PostgreSQL/Python stack in the README is planned, not present: don't pretend it exists, but don't write anything that makes it harder to land — moving to Postgres is supposed to be a serialization change, not a model change.

Run the app with ./serve.sh (or npm start from the repo root); serve.mjs serves the repo root statically, so the demo screens at the root (index, login, signup, setup, diagnostic, dashboard, concept, library) and the frontend/ modules are just files. The demo path is the point of the project — Diagnostic → Gap Map → Learning Path → Learn/Practice (concept.html) → Results, re-measured by retaking the Diagnostic from the Gap Map — keep it working, keep it inspectable, and keep the demo data readable by hand: if a change makes the artefacts harder to show a judge, it is a regression even when tests pass. The known gap: the demo's Practice runs on concept.html's in-page Concept bank rather than a Practice artefact. The separate Retest artefact kind has been removed from core/schema, the generator, and the Companion tools.
